## 1. Para Iniciantes: O que esta versão entrega?

A versão **v7.48.21** resolve o problema de repetição incômoda de mensagens de alerta no WhatsApp, Telegram e Discord (conhecido na engenharia como "fadiga de alertas").

### O Modelo Mental: O Alarme de Incêndio vs. O Lembrete de Atenção
Pense nos avisos do seu servidor como dois tipos de sensores:
1. **O Alarme de Incêndio (Severidade CRITICAL):** Se um servidor cair da rede (`offline`) ou a memória RAM chegar a 95%, o alarme precisa tocar e continuar apitando em intervalos regulares até que você tome uma atitude, porque os seus clientes estão fora do ar.
2. **O Lembrete de Atenção (Severidade WARNING):** Se um servidor estiver funcionando perfeitamente, mas com um aviso de configuração (como o Cloudflare Access bloqueando a conversa automática com a Torre Master), o sistema deve te avisar uma única vez: *"Ei, percebi isso aqui!"*. Não faz sentido esse lembrete tocar no seu celular a cada 15 minutos se nada quebrou e você já está ciente.
**Agora, na v7.48.21:** Qualquer alerta de aviso (`WARNING`) é enviado **estritamente uma única vez** por ocorrência. Ele fica registrado no histórico e só volta a falar com você quando a situação for resolvida (enviando uma mensagem verde `[RESOLVIDO]`) ou se o problema voltar a acontecer no futuro.

## 2. Nota Técnica para DevOps: Arquitetura e Blindagens Implementadas

### A. Supressão de Re-notificação em Incidentes WARNING no Sentinel
- **Problema de Spam (Alarm Fatigue):**  
  O Sentinel avalia incidentes periodicamente e aplicava o temporizador `cooldownDuration` (padrão de 15 minutos) de forma indiscriminada a qualquer incidente ativo. Em incidentes persistentes de severidade `warning` (como `node_mfa_*` e alertas preventivos de capacidade), o daemon disparava uma nova notificação a cada 15 minutos para todos os webhooks e canais cadastrados.
- **Implementação em `setupmno-control/sentinel.go`:**
  1. No loop de cooldown (`runSentinelCheckCycle`), adicionada a restrição:
     ```go
     } else if now.Sub(existing.LastAlertAt) >= cooldownDuration {
         if existing.Incident.Severity != "warning" {
             existing.LastAlertAt = now
             shouldAlert = true
         }
     }
     ```
  2. Incidentes críticos (`critical`) mantêm re-notificação periódica via cooldown para garantia de atenção do operador.
  3. Incidentes de aviso (`warning`) despacham o alerta inicial normalmente (após a histerese de confirmação) e permanecem silenciosos no mapa de incidentes até sua resolução.
  4. Ao cessar a causa da anomalia, o Sentinel dispara a notificação de resolução verde (`✅ [MNO SENTINEL RESOLVIDO]`) uma única vez, limpando o estado de forma atômica.

### B. Cobertura de Testes Automatizados (`sentinel_test.go`)
- Adicionada a suíte `TestSentinelWarningOnceSuppression` validando:
  - Incidentes `warning` com `AlertSent=true` não re-notificam após `now.Sub(LastAlertAt) >= cooldownDuration`.
  - Incidentes `critical` com `AlertSent=true` re-notificam após o cooldown.
  - Normalização despacha resolução com sucesso.

## 4. Política de Rollback e Segurança

Caso um operador necessite regredir a infraestrutura:
1. A versão estável imediatamente anterior de referência é a **`v7.48.20`** (promovida em 24/09/2026).
2. O snapshot de rollback está preservado no Git através da tag `v7.48.20` (commit `1302acec9`).
3. Como a alteração da v7.48.21 é estritamente na lógica em memória do daemon Sentinel, o rollback pode ser executado sem impacto em banco de dados ou volumes.
