## 1. Para Iniciantes — O Que Mudou e Por Quê?

### O Problema Resolvido
Na versão v7.48.5, o suporte a Redis dedicado foi validado com foco no N8N v2. No entanto, o catálogo do Setup MNO conta com diversas outras aplicações e combos que também dependem de Redis dedicado e filas em stacks independentes no Docker Swarm (como Plane, Directus, Discourse, ToolJet, Reactive Resume, Infisical, Langfuse, PhotoPrism, Dify, Evolution 2 API, EvoCRM e os combos multimáquinas de Chatwoot).  
Cada aplicação adota um padrão de nomenclatura diferente em suas variáveis de ambiente (`REDIS=`, `REDIS_HOST=`, `DISCOURSE_REDIS_HOST=`, `CACHE_REDIS_URI=`, `REDIS_CONNECTION_STRING=`), o que exigia um motor verdadeiramente universal e inteligente para que nenhuma aplicação ficasse desamparada.

### O Que Mudou na Prática
1. **Detecção Inteligente Universal:** O MNO Fleet Hub agora inspeciona profundamente qualquer arquivo YAML e qualquer variável de ambiente contendo `REDIS` ou URLs `redis://`/`rediss://`.
2. **Resolução de Serviços vs Stacks:** Se a aplicação conecta usando um hostname com underline (ex: `plane_redis`), o Fleet Hub traduz inteligentemente para o nome da stack no Docker Swarm (ex: `plane-redis`) e vincula a dependência.
3. **Suporte a Múltiplos Redis no Mesmo Combo:** Em ecossistemas como o Chatwoot + Evolution (onde há um Redis para o Chatwoot e outro para a Evolution API), o Fleet Hub detecta e migra **ambos** os Redis dedicados simultaneamente.
4. **Filas de Mensageria Dedicadas (`*-mq*`):** Stacks de mensagens dedicadas (como o RabbitMQ do Plane `${nome_app}-mq`) agora também são pré-ordenadas e migradas em conjunto.
5. **Pré-Criação de Volumes Declarados:** Garante que qualquer volume externo com atributo `name:` explícito seja criado no destino antes do deploy no Docker Swarm.

## 2. Nota Técnica para DevOps

- **Função `detect_dedicated_redis_stack` Aprimorada em 4 Fases:**
  - **Fase 1 (Inspeção Profunda de YAML):** Extração agnóstica de URLs `rediss?://` e variáveis `*REDIS*=*` com descarte de chaves de autenticação (`PASSWORD`, `TOKEN`, `PORT`, `TTL`, etc.). Teste direto e com alternância de separador (`_` e `-`) contra `docker stack ls` da origem.
  - **Fase 2 (Correlação por Token/Hash/Tag):** Varredura de stacks ativas correlacionando o hash ou tag (ex: `-ai`) com a palavra `redis`.
  - **Fase 3 (Convenções Canônicas MNO):** Avaliação de variantes `${app}-redis`, `${app}_database-redis`, `${app}_directus-redis`, `${app}_evolution-redis`, etc.
  - **Fase 4 (Multi-Stream e Deduplicação):** Emissão de fluxos múltiplos via `printf "%s\n"` com canalização por `sort -u`.
- **Filtro de Auto-Exclusão Otimizado:**
  - Estrutura `case "$app" in redis|redisinsight|redicommander|cwt_redis*|evo_redis*|redisevo*|*-redis|*_redis|cwt-redis*|evo-redis*) return 0 ;; esac` para fail closed sem loops recursivos.
- **Topologia de Inicialização no Destino:**
  - `dep_apps` e `dep_bkp` expandidos com `|| [[ "$a" == *-mq* ]] || [[ "$a" == *redisevo* ]]` para garantir que bancos de cache e filas inicializem antes dos nós de aplicação.
- **Parser AWK de Volumes Externos:**
  - Captura tanto a chave principal do volume quanto o atributo `name:`, pré-criando os volumes no nó destino antes do deploy via REST API do Portainer.
