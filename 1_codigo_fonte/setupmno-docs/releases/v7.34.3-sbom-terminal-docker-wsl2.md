# v7.34.3 candidata — SBOM visível e SRE-3 funcional no WSL2

- Estado documental: `implemented`
- Maturidade: `beta`
- Data: 26/08/2026
- Última versão estável preservada: `v7.33.4`

## Para iniciantes

Esta correção resolve dois sintomas diferentes. Primeiro, o painel dizia que o
SBOM não estava disponível mesmo quando os quatro arquivos de segurança já
estavam instalados e válidos. SBOM significa *Software Bill of Materials*: uma
lista dos componentes usados para montar o software, semelhante à lista de
ingredientes de um produto.

Segundo, no WSL2 o Terminal Seguro não conseguia conversar com o Docker Desktop.
Pense no socket Docker como uma porta interna com uma chave de grupo. A porta
estava montada, mas o terminal não recebia a chave numérica usada pelo Windows.
A v7.34.3 entrega essa chave somente ao Terminal Seguro autenticado.

## O que mudou

- o estado verde de SBOM e supply chain não é mais apagado por uma atualização
  posterior do catálogo que não possui esses campos;
- instalações novas adicionam ao Terminal Seguro o grupo numérico real de
  `/var/run/docker.sock`;
- instalações existentes recebem o mesmo reparo durante a reconciliação,
  inclusive quando as imagens já estavam atualizadas;
- o valor é salvo no próprio serviço para permitir remover com segurança um
  grupo antigo caso o Docker Desktop o altere;
- o resultado final do SRE-3 usa linguagem humana: cobertura parcial é exibida
  como limitação de medição, não como vulnerabilidade confirmada;
- Setup MNO `7.34.3` e Control Center `4.34.2`.

## O que permaneceu igual

- SRE-3, Assistente MNO e Blueprints continuam BETA;
- o Assistente, a LLM, o painel e o agente continuam sem Docker socket, shell,
  sudo, root de produção ou grupo Docker;
- somente o Terminal Seguro, já autenticado e confirmado pelo usuário, recebe
  o grupo adicional;
- Trivy e Lynis continuam sem socket; somente o Docker Bench temporário recebe
  o socket durante a auditoria confirmada;
- nenhum scanner aplica correção, reinicia aplicação ou altera configuração;
- resultados brutos são apagados e apenas contagens sanitizadas válidas por 24
  horas são persistidas;
- a v7.33.4 continua sendo a versão estável até nova declaração explícita.

## Como testar no WSL2

Pré-requisitos: Docker Desktop iniciado, integração WSL2 habilitada, Swarm ativo
e Control Center reconciliado para `4.34.2`.

1. Abra **Catálogo de setups** e atualize a página.
2. Confirme que a faixa de supply chain está verde e informa SBOM, inventário,
   atestação e manifesto válidos.
3. Abra **Assistente MNO > Motores determinísticos · BETA**.
4. Execute a auditoria e confirme no Whiptail.
5. Valide o resumo sanitizado:

```bash
sudo jq '{hostType,overallStatus,complete,engines:[.engines[]|{id,status,counts,limitations}]}' \
  /root/SetupLowCodeMno/.control/sre-engine/latest.json
```

Resultado esperado: `hostType` igual a `wsl2`; nenhum motor `failed`; Trivy com
ao menos uma imagem, Lynis com testes e Docker Bench com contagens. É normal
obter `overallStatus:"incomplete"` e `complete:false` quando um motor informa
`partial`: isso significa que parte dos controles não pôde ser medida.

Sinal de falha: erro de permissão ao conectar em `/var/run/docker.sock`, todos
os motores `failed`, Trivy com zero imagens e sem limitação declarada, ou a faixa
SBOM permanecer indisponível depois da reconciliação.

## Como testar na VPS

Repita o teste do catálogo e da auditoria em Debian/Ubuntu. O grupo do socket
normalmente é diferente do WSL2, mas deve ser detectado automaticamente. Em
instalação Tradicional, execute o motor por SSH; o Terminal Seguro remoto
continua proibido.

## Riscos e proteções

Conceder acesso ao socket Docker equivale a uma permissão administrativa. Por
isso ele não foi entregue ao Assistente nem aos scanners que não precisam dele.
O reparo é limitado ao serviço do Terminal Seguro, usa um número validado do
socket real e só remove um grupo antigo que tenha sido registrado anteriormente
pelo Setup MNO.

## Rollback

Restaure o commit ou pacote candidato anterior e reconcilie o Control Center.
O rollback troca apenas código e especificação do serviço; não exige apagar
stacks, bancos, volumes ou aplicações. A volta remove a correção de acesso ao
socket no WSL2, portanto o SRE-3 poderá retornar a `failed` nesse ambiente.
