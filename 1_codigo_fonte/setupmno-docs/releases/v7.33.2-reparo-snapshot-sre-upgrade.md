# v7.33.2 — Reparo do snapshot SRE após atualização

- Versão: 7.33.2
- Estado: `implemented`
- Maturidade: `beta`
- Atualizado em: 2026-08-24
- Responsável: Francis MNO
- Ambientes: WSL2 e VPS com Docker Swarm
- Arquiteturas: x86-64 e ARM64
- Planos afetados: todos os planos autenticados

## Para iniciantes

O Assistente MNO pede ao agente interno uma fotografia segura do servidor. Essa
fotografia contém somente informações permitidas, como memória, disco, versões
e quantidade de serviços. Em uma instalação antiga atualizada para a v7.33.1,
o agente ficou sem a identificação da versão do Control Center. Por segurança,
o painel recusou a fotografia e mostrou `Falha HTTP 502`.

A v7.33.2 garante que a versão seja entregue ao agente em todas as atualizações.
Ela também repara automaticamente instalações antigas que perderam essa
informação.

## Modelo mental

Imagine um porteiro que só aceita um relatório quando ele vem com data e número
de edição. O conteúdo estava correto, mas a etiqueta da edição estava ausente.
O porteiro recusou o relatório. Agora o atualizador confere o conteúdo e a
etiqueta antes de dizer que tudo já está sincronizado.

## O que mudou

- o atualizador grava `APP_VERSION` no agente interno;
- uma versão anterior é removida antes de gravar a nova, evitando duplicidade;
- a ausência ou divergência da versão impede o falso resultado “já está
  sincronizado”;
- a atualização continua no mesmo serviço Docker, sem recriar a stack;
- testes cobrem os estados sem versão, versão antiga e versão correta.

## O que permaneceu igual

- o agente continua somente leitura e sem comando genérico de shell;
- o painel e o Assistente continuam sem acesso ao Docker Socket;
- nenhuma aplicação, volume, banco, DNS ou rota Cloudflare é alterada;
- o Especialista SRE e o Assistente MNO continuam identificados como BETA;
- erro do provedor de linguagem é separado do snapshot local. Um HTTP 429 do
  OpenRouter significa limite temporário do provedor, não defeito no Docker.

## Nota técnica para DevOps

O `control-upgrade.sh` reconcilia a variável de ambiente `APP_VERSION` no
serviço `mnoctrl...-agent`. O caminho de retorno antecipado, chamado de
`noop`, agora exige imagem correta e versão semântica exata no agente. Assim,
uma instalação legada com a imagem certa e metadado ausente não é ignorada.

O validador do snapshot mantém o comportamento de negação segura: uma versão
ausente continua inválida. A correção está no provisionamento, não no
afrouxamento da validação.

## Como testar no WSL2

Pré-requisitos: Docker Desktop integrado ao WSL2 e Control Center atualizado.

1. Confirme que os serviços estão ativos:

   ```bash
   docker service ls --format '{{.Name}} {{.Replicas}}' | sort
   ```

2. Confirme a versão do agente, substituindo o nome fictício pelo serviço real:

   ```bash
   docker service inspect mnoctrlEXEMPLO-agent_mnoctrlEXEMPLO-agent \
     --format '{{range .Spec.TaskTemplate.ContainerSpec.Env}}{{println .}}{{end}}' \
     | grep '^APP_VERSION='
   ```

3. Resultado esperado na v7.33.2:

   ```text
   APP_VERSION=4.33.2
   ```

4. No Control Center, abra **Assistente MNO** e clique em **Analise a saúde do
   servidor**.
5. O resultado deve exibir um diagnóstico local ou uma contingência local. Não
   deve aparecer HTTP 502 causado pelo snapshot.

Sinal de falha: ausência de `APP_VERSION`, réplica do agente diferente de
`1/1` ou nova mensagem HTTP 502. Um erro HTTP 429 deve ser investigado no
provedor de LLM separadamente.

## Como testar em uma VPS

1. Atualize uma instalação de homologação para a v7.33.2.
2. Repita a inspeção de `APP_VERSION` acima.
3. Confirme que o agente e o painel alcançam `1/1` réplica.
4. Execute o botão de análise no navegador em uma sessão autenticada.
5. Repita em uma instalação nova e em uma instalação que veio da v7.33.1.

Resultado esperado: ambos os caminhos entregam `APP_VERSION=4.33.2` ao agente e
o snapshot SRE é aceito.

## Erros comuns

- **HTTP 429:** o provedor de LLM atingiu um limite; aguarde ou revise a conta.
- **HTTP 502 com agente 0/1:** primeiro corrija a inicialização do serviço.
- **Imagem correta, versão ausente:** a atualização não reconciliou os
  metadados; consulte o log técnico do atualizador.
- **Página antiga no navegador:** faça uma atualização completa com `Ctrl+F5`.

## Riscos, limites e proteções

- a mudança reinicia somente a tarefa do agente durante a reconciliação;
- o snapshot pode ficar indisponível por alguns segundos enquanto a réplica
  volta a `1/1`;
- o reparo não resolve indisponibilidade ou limite comercial do OpenRouter;
- a validação de versão continua bloqueante para não aceitar dados de um agente
  incompatível;
- nenhuma credencial é adicionada ao serviço ou registrada nos testes.

## Rollback

Não há migração de dados. Para desfazer a versão, reverta o commit da v7.33.2,
regenere os pacotes e aplique a versão anterior pelo fluxo oficial. O Docker
Swarm também mantém o mecanismo de rollback do serviço caso uma atualização não
atinja a réplica esperada. Não remova variáveis manualmente em produção como
forma permanente de rollback.

## Como explicar para a comunidade

“O diagnóstico seguro já funcionava, mas algumas instalações atualizadas
ficavam sem a etiqueta de versão no agente interno. O Setup recusava esses dados
por segurança e mostrava 502. A v7.33.2 corrige o atualizador e faz essa
conferência automaticamente, sem liberar novos poderes para a IA.”
