## 1. Para Iniciantes: O que mudou?

### Qual problema foi resolvido?
Quando você formatava um servidor novo, configurava ele como **Nó Operário** e ativava o **Cloudflare MFA**, ao voltar para a **Torre Master** (no seu WSL2 ou VPS principal) e cadastrar esse nó no **MNO Fleet Hub**, aparecia um aviso em vermelho dizendo **"MFA BLOQUEANDO"**.  
A Torre de Controle não conseguia ler o uso de memória, CPU ou status dos aplicativos daquele servidor porque a Cloudflare achava que a Torre Master era uma pessoa tentando abrir o painel pelo navegador sem digitar o código do aplicativo autenticador.

### Modelo Mental: A "Portaria com Crachá" vs a "Entrada dos Correios"
Pense no seu servidor como um prédio comercial:
- A porta principal (onde os clientes e você entram) tem uma portaria com segurança máxima que pede login, e-mail e código de 6 dígitos no celular (**Cloudflare MFA**).
- Mas a Torre Master não é uma pessoa: ela é como um carteiro de confiança que entrega malotes entre as filiais e a sede. Ela não tem celular para digitar código no navegador; ela possui uma **Chave Criptográfica Secreta** (o **Token da Frota**) que só a sua Torre e o seu servidor conhecem.
- O que aconteceu: a Cloudflare estava fechando todas as entradas com a porta dos humanos.
- O que a **v7.48.26** faz: o Setup MNO cria automaticamente uma entrada reservada e exclusiva para o malote da frota (`/api/fleet/*`). A porta principal continua 100% trancada com MFA para qualquer pessoa na internet, mas a Torre Master passa direto pela entrada técnica usando o Token Secreto. E o melhor: você não precisa configurar absolutamente nada na mão!

## 2. Nota Técnica para DevOps

- **Correção da Sintaxe da API Cloudflare Access (`everyone`):**
  - **Causa Raiz:** Em `cloudflare-mfa.sh`, a chamada de criação de aplicação e política de Bypass enviava `include: [{everyone: true}]`. A API v4 da Cloudflare rejeita esse payload com o erro HTTP 400 (`invalid 'include' configuration', code 12130`).
  - **Correção:** Atualizado para `include: [{"everyone": {}}]`, em estrita conformidade com a especificação canônica da Cloudflare Zero Trust Access API.
- **Remoção de Interceptação Indesejada no Cloudflare Tunnel (`originRequest.access`):**
  - **Causa Raiz:** Ao injetar `access: {required: true, ...}` na configuração do ingress do túnel, o conector local `cloudflared` rejeita com HTTP 403 requisições que chegam sem cookie ou header JWT (`Cf-Access-Jwt-Assertion`). Como políticas de Bypass na borda da Cloudflare propositalmente não geram JWT, o próprio túnel bloqueava a rota `/api/fleet/*`.
  - **Correção:** Em nós com papel de Nó Operário (`fleetMode == "worker"`), a diretiva `originRequest.access` é suprimida da rota do painel no túnel. A proteção de borda do Cloudflare Access permanece íntegra para o domínio, e o backend em Go valida o JWT para sessões web (`ACCESS_JWT_REQUIRED=true`), enquanto a rota `/api/fleet/worker/*` é protegida pelo header `X-SetupMNO-Fleet-Token`.
- **Automação Idempotente de Provisionamento nos Dois Fluxos:**
  - **Fluxo A (Nó Operário antes, MFA depois):** Ao ativar o MFA no menu (`configure_existing_access_mfa`), o instalador detecta `fleetMode == "worker"`, atualiza a rota do túnel e invoca automaticamente `manage_access_bypass_cli add-telemetry`.
  - **Fluxo B (MFA antes, Nó Operário depois):** Ao comutar o servidor para Nó Operário em `fleet-mode.sh` (Opção 3), o script verifica se o MFA já está ativo e executa automaticamente `setupmno_control.sh --add-telemetry-bypass`.
- **Controle Estrito de Tamanho:**
  - `installer-template.sh` preservado com 122.598 bytes (margem de 282 bytes abaixo do teto de 122.880 bytes).
  - Paridade rigorosa entre as árvores `x86` e `arm`.
