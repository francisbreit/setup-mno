## Para iniciantes

A versão **v7.47.0** entrega a **Fase 2 do Fleet Clone**, focada na automação completa de aplicações baseadas no banco de dados **MySQL 8.0** (como WordPress, HumHub, BookStack, Mautic 4, Mautic 5 e Mautic 6).

### O problema que foi resolvido
Imagine que você tem um site WordPress na sua Torre Master local (WSL2) e quer migrá-lo para uma VPS na nuvem com um clique. No servidor de origem, a senha do banco de dados era "Senha123". No servidor de destino, o MySQL já instalado usa a senha "Senha456". 
Nas ferramentas comuns de mercado (Coolify, Dokku, scripts de YouTube), a migração copia os arquivos, mas o WordPress não liga e dá o famoso erro: *"Error establishing a database connection"*. Isso acontecia porque o arquivo de configuração do WordPress (`wp-config.php`) continuava com a senha antiga. Além disso, se o destino nem tivesse o MySQL instalado, a migração quebrava.

### O que o Setup MNO v7.47.0 faz por você
1. **Provisionador Automático de MySQL 8.0:** Antes de restaurar a aplicação, o sistema verifica se o servidor de destino já possui o MySQL 8.0 ativo. Se não tiver, ele instala e inicia a stack oficial do MySQL (`mysql_mysql`) automaticamente, aguarda o banco ficar pronto e saudável, e só então prossegue.
2. **Despejo e Restauração Segura com Compressão:** O banco de dados de origem é exportado em formato compactado (`.sql.gz`) via túnel seguro, sem expor dados nem sobrecarregar o disco.
3. **Auditoria Imediata Pós-Restauração:** O sistema roda uma checagem em tempo real (`SHOW DATABASES LIKE`) para garantir que 100% das tabelas e dados foram gravados antes de ligar a aplicação. Se algo falhar, o processo aborta de forma segura sem corromper o servidor.
4. **Reconciliação Dinâmica de Senhas (Zero Toque Manual):** O sistema injeta a senha correta do MySQL do destino tanto nas variáveis da aplicação (`stack.yaml`) quanto nos arquivos internos de configuração gravados dentro do volume persistente (`wp-config.php` do WordPress e `local.php` do Mautic). A aplicação já sobe conectada e funcionando de primeira!

## Nota técnica para DevOps: O que mudou e foi homologado

- **Segregação Estrita entre MySQL 8.4 e MySQL 8.0:**
  - O Mautic 7 utiliza o Percona Server 8.4 sob a stack `mysql84` (serviço `mysql84_mysql84`).
  - As demais aplicações MySQL (WordPress, HumHub, BookStack, Mautic 4/5/6) utilizam a stack `mysql` (serviço `mysql_mysql`, imagem `percona/percona-server:8.0`).
  - Os filtros de container e inspeção foram ajustados para evitar colisões entre as duas versões usando labels Swarm e exclusão mútua (`grep -v 'mysql84'`).
- **Função `ensure_mysql_ready`:**
  - Implementada para gerenciar o ciclo de vida da stack MySQL 8.0 no destino (`local` ou via SSH).
  - Prioriza a descoberta de senha do Portainer (`portainer.txt`) e inspeciona variáveis de ambiente ativas ou arquivos `/root/mysql.yaml`.
  - Gera credencial segura via `openssl rand -hex 16` caso inexistente.
  - Aguarda a prontidão operacional do motor executando `mysql -u root -e "SELECT 1;"` em loop de polling até 30 segundos com fail-closed.
- **Detecção e Exportação Lógica em Stage 65%:**
  - Atualização do `detect_database_engine` para identificar dependências MySQL padrão (`mysql:<app>`) e registrar `db_type="mysql"` no manifesto de migração.
  - Criação do snapshot lógico comprimido `db_logical_dump.sql.gz` utilizando `mysqldump` com flags `--single-transaction --quick`.
- **Restauração e Gate de Integridade em Stage 75%:**
  - Criação condicional do esquema com `CREATE DATABASE IF NOT EXISTS`.
  - Ingestão do dump via pipeline desacoplada `gunzip -c | docker exec -i`.
  - Verificação de sanidade pós-importação com `SHOW DATABASES LIKE '$my_dbname'`.
- **Reconciliação de Credenciais em Storage Persistente:**
  - Atualização dinâmica das variáveis de ambiente na stack (`WORDPRESS_DB_PASSWORD`, `DB_PASSWORD`, `MYSQL_PASSWORD`, etc.).
  - Execução de container efêmero Alpine para patch in-place via `sed -i` diretamente no arquivo de configuração residente no volume persistente (`wp-config.php` no volume `${cur_app}` e `local.php` no volume `${cur_app}-config`).
- **Paridade Rigorosa e Verificação Estática:**
  - Validado em Bash x86 e ARM64 com paridade estrita (`diff -u` idêntico).
  - Testado contra matriz determinística de 897 evals do Setup MNO.

## Segurança, política de rollback e baseline estável

### Versão Estável de Referência
- A versão **v7.45.0** permanece como a versão estável homologada anterior de referência.
- A versão **v7.47.0** consolida a Fase 2 do Fleet Clone em estado `beta` de homologação.

### Procedimento de Rollback
Caso qualquer teste de migração de aplicações MySQL necessite de reversão:
1. Os dados originais na máquina de origem nunca são alterados nem deletados;
2. No servidor de destino, basta executar `docker stack rm <nome_da_aplicacao>` para remover a aplicação sem afetar o banco MySQL compartilhado;
3. Se a stack `mysql` tiver sido criada pelo provisionador e não houver outras aplicações nela, pode ser removida com `docker stack rm mysql`.
