## 1. Para Iniciantes — O Que Mudou e Por Quê?

### O Problema Resolvido
No Setup MNO, ferramentas como o **n8n v2 (Editor, Webhook, Worker, MCP)** e certos combos utilizam uma base de dados em memória chamada **Redis Dedicado** (por exemplo, `n8na8ebda2-redis`), que funciona como uma fila ultrarrápida para que os fluxos não se percam.  
Na lógica anterior de migração do Fleet Hub, o sistema procurava apenas ferramentas irmãs com o mesmo sufixo no final do nome. Como o Redis do n8n v2 termina em `-redis` (e não com o código de 7 caracteres no fim), ele acabava ficando para trás na Torre Master de origem! Além disso, se o usuário optasse por migrar apenas uma stack individual do combo, o Redis não ia junto, fazendo com que o n8n no nó destino falhasse ao iniciar.

### Modelo Mental / Analogia
Imagine que você vai mudar de casa e contratou o caminhão de mudança para levar a sua geladeira duplex. O motor do n8n v2 é o corpo da geladeira, e o Redis dedicado é o motor/compressor que vai acoplado atrás dela. Não adianta levar só o armário da geladeira para a casa nova e deixar o motor na casa antiga: ela não vai funcionar! A versão v7.48.5 garante que, ao levar a aplicação, o motorzinho dedicado (Redis) vai compulsoriamente junto, perfeitamente parafusado e conectado.

### O Que Mudou na Prática
1. **Identificação Automática:** Qualquer aplicação ou combo que possua Redis dedicado (como o n8n v2) é imediatamente detectada pelo Fleet Hub.
2. **Migração Compulsória e Ordenada:** O Redis dedicado vai compulsoriamente junto tanto na migração de **Combo Completo** quanto na de **Aplicação Única**.
3. **Ordem de Inicialização Perfeita:** O Redis dedicado sobe primeiro no nó de destino para já estar pronto e aguardando conexões antes das aplicações dependentes ligarem.
4. **Preservação de Dados e Volumes:** O volume persistente de dados do Redis dedicado (ex: `n8na8ebda2-redis-data`) é transportado, restaurado e validado no destino.

## 2. Nota Técnica para DevOps

- **Expressão Regular Flexível para Hash de Instância:** O regex de detecção em `detect_app_combo_context` foi expandido de `([a-f0-9]{7})$` para `([a-f0-9]{7})` com match agnóstico `[[ "$s" == *"$app_suffix"* ]]`, reconhecendo stacks irmãs onde o hash de 7 dígitos hexadecimal encontra-se em posição intermediária (como `n8na8ebda2-redis`).
- **Função Especializada `detect_dedicated_redis_stack`:**
  - Varre o Docker Swarm em busca de stacks irmãs contendo `${app_suffix}` e `redis`.
  - Inspeciona o Compose/YAML da aplicação procurando variáveis de fila e cache: `QUEUE_BULL_REDIS_HOST`, `REDIS_HOST`, `REDIS_URL`, `CACHE_REDIS_HOST`.
  - Fallback por convenção: `${app_name}-redis`.
- **Anexação Obrigatória via `attach_dedicated_redis_to_list`:**
  - Mesmo quando o operador seleciona a Opção 2 (*"Migrar apenas esta aplicação"*), a stack de Redis dedicado é obrigatoriamente anexada à fila de deploy (`apps_to_migrate`) e de backup (`apps_to_backup`).
- **Desbloqueio de Volumes no `get_application_volumes`:**
  - O filtro que ignorava volumes com prefixo `redis*` foi estritamente restrito para descartar somente o volume compartilhado global `redis_data`. Volumes dedicados como `n8na8ebda2-redis-data` ou `redisevo-data` são preservados e empacotados integralmente.
- **Pré-criação de Volumes Externos no Swarm:**
  - O Docker Swarm rejeita o deploy de stacks cujos volumes estão declarados como `external: true` se o volume não existir previamente no host. O `fleet-clone.sh` agora audita os volumes externos no YAML e executa `docker volume create <nome>` preventivamente no destino antes de chamar `deploy_stack_with_portainer_priority`.
- **Compatibilidade Go Backend (`setupmno-control`):**
  - O método `detectAppComboContextGo` em `1_codigo_fonte/setupmno-control/fleet_transfer.go` foi sincronizado para extrair blocos hexadecimais de 7 dígitos em qualquer posição do nome da stack.
