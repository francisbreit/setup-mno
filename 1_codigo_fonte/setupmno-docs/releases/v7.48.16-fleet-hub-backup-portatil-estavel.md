## 1. Para Iniciantes: O que esta versão entrega?

A versão **v7.48.16** é um dos maiores saltos de maturidade da história do **Setup MNO**. Ela resolve de ponta a ponta o desafio de salvar, transportar e restaurar aplicações inteiras entre servidores diferentes de forma confiável e sem depender de conhecimentos avançados de Linux.

### O Modelo Mental (O "Pendrive Mágico" do Setup MNO)
Imagine que antes, para mudar uma aplicação de um servidor para outro, você precisava desmontar um armário inteiro peça por peça: fazer backup do banco de dados, copiar arquivos de mídia, recriar usuários e senhas, reconfigurar portas e torcer para nada quebrar no caminho.

Com o **Backup Portátil Universal** da v7.48.16, o Setup MNO funciona como um "pendrive mágico" em formato `.tar.gz`:
1. Você vai no servidor de origem (mesmo que seja um Worker remoto subordinado), clica em **Criar Backup Portátil** e ele empacota tudo sozinho: banco de dados, arquivos de mídia, volumes Docker, arquivos de configuração do Swarm e até imagens especiais criadas sob medida na hora da instalação.
2. Você move esse único arquivo `.tar.gz` para outro servidor (sua Torre Master ou outra VPS).
3. No servidor de destino, você seleciona **Restaurar Backup Portátil** e clica em `<Ok>`.
4. O Setup MNO descompacta, carrega as imagens, reconcilia as senhas dos bancos, sobe os containers no Docker Swarm e só avisa que terminou quando **todos os containers realmente estiverem ligados e funcionando**.

## 2. Nota Técnica para DevOps: Bateria de Blindagens Implementadas

### A. Empacotamento de Imagens Customizadas Locais (Caso Mautic 7)
- **Problema Anterior:** Aplicações com builds locais ou imagens customizadas (como o Mautic 7 WhatsMkt gerado em tempo de setup) não tinham imagem disponível em repositórios remotos (Docker Hub). Na restauração em outro nó, o Swarm falhava silenciosamente em `No such image: mautic7whatsmkt:latest`.
- **Solução:** O `action_backup_app` agora inspeciona todas as imagens do manifesto da stack:
  ```bash
  docker image inspect "$img" ...
  docker manifest inspect "$img" ...
  ```
  Se a imagem existir localmente e falhar na inspeção do registro remoto, ela é automaticamente exportada via `docker save "$img"` e compactada em `images/img_<hash>.tar.gz` dentro do pacote `.tar.gz`.
- **Restauração Automática:** O `action_restore_backup` detecta o diretório `images/` e executa `docker load` no nó de destino antes de disparar o `docker stack deploy`.

### B. Eliminação de Falsos Positivos com Gate de Convergência Real
- **Problema Anterior:** A restauração antiga executava o deploy da stack e exibia imediatamente uma tela verde de sucesso, antes que os containers terminassem de inicializar. Se a imagem faltasse ou a porta colidisse, o usuário recebia falso positivo de sucesso.
- **Solução:** Foi criado um **Gate de Convergência com Polling de Réplicas** no Swarm:
  - Monitora o estado de réplicas esperadas vs réplicas ativas (`replicas_running / replicas_desired`).
  - Aguarda até 35 segundos para estabilização de serviços pesados.
  - Se algum container não convergir, registra em `convergence_errors.txt` e apresenta relatório detalhado ao usuário com o comando exato de diagnóstico (`docker service ps <servico> --no-trunc`).

### C. Reconciliação Automática de Motores MySQL (8.4 vs 8.0)
- Aplicações que utilizam MySQL agora passam por reconciliação automática de senhas e permissões (`GRANT ALL PRIVILEGES`) no banco do destino, eliminando falhas de conexão de banco decorrentes de migrações entre nós com engines divergentes.

### D. Solução Definitiva de OOM (Out-Of-Memory) no Backup via Terminal Web
- **Problema Anterior:** Durante a criação de backups grandes pelo terminal web do Control Center, o processo era subitamente abortado pelo Linux com `Killed`.
- **Causa Raiz:** O diretório temporário `$tmpdir` era criado em `/tmp`, que no container operava em `tmpfs` (memória RAM), e o container possuía limite de 256MB de memória.
- **Solução:**
  1. O `tmpdir` foi transferido para `$BACKUP_BASE_DIR` (`/root/setupmno-backups/`), gravando diretamente em disco físico ext4 (mais de 50GB livres).
  2. O limite de memória do serviço de terminal web `mnoctrl...-terminal` foi quadruplicado de 256MB para 1024MB no compose do instalador.

### E. Blindagem Matemática de Traps RETURN e Resolução de `unbound variable`
- **Causa Raiz:** No interpretador Bash com `set -uo pipefail`, traps atreladas ao sinal `RETURN` não são locais à função e continuavam ativas disparando no retorno de subfunções chamadas pelo menu principal (`show_menu`) ou Raio-X (`action_inspect_nodes`), tentando ler variáveis locais já destruídas da memória.
- **Solução em 5 Camadas:**
  1. **Auto-desarme atômico:** Primeira instrução da trap é `trap - RETURN;`.
  2. **Expansão defensiva:** Uso de `${chosen_dest_id:-local}` e `${tmpdir:-}` em todas as traps.
  3. **Limpeza explícita:** Chamada de `trap - RETURN` no encerramento de todas as ações.
  4. **Declaração antecipada:** Inicialização de variáveis no cabeçalho das funções.
  5. **Barreira de contenção no loop:** Desarme preventivo em cada ciclo do menu `show_menu`.

### F. Blindagem Visual com `clear` e Reset de Sessões `tmux` Obsoletas
- **Problema:** A tela preta do terminal exibia por 1 segundo textos residuais de comandos anteriores durante a transição entre caixas de diálogo do Whiptail. Além disso, a persistência do `tmux` no terminal web mantinha processos antigos rodando em memória segurando inodes marcados como `(deleted)`.
- **Solução:**
  1. Inserção de `[ -t 1 ] && clear 2>/dev/null || true` na entrada de todas as funções interativas e transições de tela.
  2. Procedimento de expurgo e reset de sessões antigas para assegurar que apenas código novo seja executado.
